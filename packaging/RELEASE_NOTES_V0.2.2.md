# FileCheck v0.2.2

FileCheck v0.2.2 是针对历史备份再次进入扫描/备份/删除链路的安全修复版本，建议所有使用 v0.2.x 的用户升级。

## 修复：切换备份根目录后，旧备份可能再次被扫描

此前 FileCheck 在扫描阶段会排除“当前配置的备份根目录”。如果用户之后切换备份根目录，或者将旧备份批次移动到其他磁盘/目录，旧备份中的文件仍可能被 Everything 索引命中。

如果用户继续对这些候选执行备份，并随后执行源文件删除，理论上可能形成“备份旧备份 → 删除旧备份中的文件”的危险链路。

v0.2.2 将历史备份识别从“依赖当前备份根目录”升级为“基于备份自身身份识别”，并在多个阶段增加独立保护。

## v0.2.2 的保护机制

### 1. 新备份批次增加持久身份标记

新创建的正式备份批次会包含：

```text
.filecheck-backup
manifest.json
files\...
```

`.filecheck-backup` 记录 FileCheck 备份格式、版本和 batch_id。即使整个备份批次之后被移动或重命名，FileCheck 仍可识别其备份身份。

### 2. 旧版本备份继续受保护

v0.2.1 及更早版本没有 `.filecheck-backup` 标记。v0.2.2 会继续通过有效 `manifest.json`、`batch_id`、`files` 目录以及原批次目录名识别旧备份，因此现有备份无需迁移或重新制作。

### 3. 扫描结果阶段自动过滤历史 FileCheck 备份

Everything 即使返回了历史备份中的文件，FileCheck 也会在候选结果阶段再次判断该路径是否位于 FileCheck 备份批次内。

位于历史备份中的候选会被自动剔除，并在扫描日志/结果中记录排除数量和涉及的备份批次。

此保护不依赖该批次是否仍位于当前配置的 backup root。

### 4. 核心备份入口再次阻断备份嵌套

即使通过 CLI、旧扫描结果或其他入口直接向 `create_backup()` 提交历史备份中的文件，核心备份逻辑也会拒绝继续。

如果用户选择的普通目录内部包含完整 FileCheck 历史备份，同样会拒绝创建新备份，避免把历史备份再次作为普通文件树复制。

### 5. 源文件删除阶段增加最终硬保护

删除预检、正常删除、快速删除和断点续删都会再次检查 source_path。

任何仍位于 FileCheck 历史备份中的路径都禁止作为普通源文件删除。即使旧任务状态或异常路径绕过了扫描/备份阶段，这一层仍会阻止实际删除。

### 6. 删除调用返回后确认文件确实消失

删除逻辑现在不会只依赖 `unlink()` 没有抛异常来判断成功。删除调用返回后会再次检查路径是否仍存在；只有确认路径已经不存在才记录为 `deleted`。

如果路径仍存在，则记录为失败并保留文件。

## 恢复语义保持不变

本版本没有尝试自动重写历史 `manifest.source_path`，也不会猜测“多层备份历史”中的恢复目标。

恢复仍严格按照当前备份 manifest 记录的原始路径执行，这样可以避免自动推断造成新的路径歧义或覆盖风险。

## 兼容性

- `manifest.json` schema version 仍为 1；
- v0.2.0 / v0.2.1 现有备份仍可验证、删除源文件状态检查和恢复；
- 新增 `.filecheck-backup` 只用于备份身份识别，不改变备份文件内容和 SHA-256 语义；
- v0.2.1 的 Windows 7 深层目录紧凑存储和短原子临时文件机制继续保留；
- Everything 专用数据库格式不变；
- GUI 与 CLI 继续共用同一套核心安全逻辑。

## 边界条件回归测试

本版本新增并验证：

- 新备份标记可正确识别；
- 备份批次移动并重命名后仍被识别；
- 旧版本无标记备份仍受保护；
- 仅仅目录名类似 `FC-*`、但结构无效的普通目录不会被误判；
- 切换 backup root 后，历史备份中的 Everything 候选仍会被过滤；
- 直接选择历史备份中的文件执行新备份会被拒绝；
- 选择一个内部包含历史 FileCheck 备份的大目录会被拒绝；
- 删除预检会拒绝历史备份中的 source_path；
- 即使绕过预检，删除运行时硬保护仍会阻断；
- `unlink()` 返回但文件实际仍存在时不会误报删除成功；
- Windows / Ubuntu Python 3.10 与 3.12 完整测试通过；
- Python 3.8 Win7 GUI 兼容构造检查通过。
