# FileCheck GUI 设计规范

> 适用范围：`src/filecheck/gui/` 下全部界面。任何新增页面都必须遵守本规范。

## 1. 设计目标

FileCheck 是面向 Windows 桌面环境的文件检查、备份、迁出和恢复工具。GUI 设计优先级如下：

1. 操作路径清晰，危险动作可辨识。
2. Win7 / Win10 常见分辨率下保持稳定可读。
3. 页面视觉统一，禁止各页面自行发明颜色、字体、间距和圆角。
4. 保持工具软件的专业感，避免过度动画、透明、渐变和装饰。
5. GUI 只负责交互与状态展示，业务逻辑继续复用现有核心模块。

## 2. 视觉基线

### 2.1 风格

- 默认浅色主题。
- 蓝灰色专业工具风格。
- 使用白色卡片承载主要信息，页面背景使用浅灰蓝。
- 首版不使用阴影、渐变、毛玻璃和复杂动画，以保证 Windows 兼容性。
- 首版不依赖特殊图标字体；需要图标时统一使用项目内 PNG 资源。

### 2.2 色彩

所有颜色必须从 `gui/tokens.py::Palette` 引用。

- 主色：`#2563EB`
- 主色悬停：`#1D4ED8`
- 页面背景：`#F4F7FB`
- 卡片背景：`#FFFFFF`
- 次级背景：`#F8FAFC`
- 边框：`#E2E8F0`
- 主文字：`#0F172A`
- 次文字：`#475569`
- 弱文字：`#94A3B8`
- 成功：`#15803D`
- 警告：`#B45309`
- 危险：`#B91C1C`

危险操作只能使用危险色；普通主按钮不得使用红色。

## 3. 字体层级

统一使用 `Microsoft YaHei UI`，由 `gui/tokens.py::Typography` 管理。

- 页面标题：28 / Bold
- 区块标题：18 / Bold
- 卡片标题：16 / Bold
- 正文：14 / Normal
- 辅助说明：13 / Normal
- 小标签：12 / Normal

页面代码不得直接声明字体名称和字号。

## 4. 间距与尺寸

采用 4 / 8 基础网格：`4, 8, 12, 16, 24, 32, 40`。

- 左侧导航宽度：224 px
- 页面外边距：28 px
- 卡片内边距：20~24 px
- 控件标准高度：38 px
- 主按钮高度：40 px
- 卡片圆角：14 px
- 控件圆角：8 px
- 小标签圆角：6 px

统一从 `Spacing / Radius / Layout` 引用。

## 5. 页面结构

所有一级页面遵循相同骨架：

1. `PageHeader`：标题 + 一句说明。
2. 主要工作区：一个或多个 `Card`。
3. 页面主操作靠近对应卡片，不把无关按钮堆在顶部。
4. 同一区域最多一个主按钮；次要动作使用次级按钮。
5. 页面底部不重复全局状态，全局状态由主窗口状态栏统一显示。

## 6. 公共组件

页面优先使用 `gui/components.py` 中的组件：

- `PageHeader`
- `Card`
- `PrimaryButton`
- `SecondaryButton`
- `DangerButton`
- `DangerConfirmDialog`
- `StatusPill`
- `SidebarButton`
- `MetricCard`
- `EmptyState`

如果某控件在两个及以上页面重复出现，应先抽成公共组件再继续开发。

## 7. 导航规范

固定一级导航：

- 首页
- 扫描
- 扫描结果
- 备份与迁出
- 源文件处理
- 恢复
- 设置

“源文件处理”必须保持为独立一级页面，不与普通备份按钮混在同一卡片内。当前页面使用主色浅背景和主色文字突出。

## 8. 状态与危险操作

状态统一分为：

- `neutral`：普通/未开始
- `info`：执行中/提示
- `success`：成功
- `warning`：需关注
- `danger`：失败或高风险

删除源文件、覆盖恢复等不可逆或高风险动作必须：

1. 使用危险按钮样式；
2. 明确显示影响文件数量；
3. 使用 `DangerConfirmDialog` 二次确认，并要求输入固定确认词；
4. 不得在 GUI 主线程执行；
5. 删除必须持续记录可恢复/可续作状态，取消只能发生在状态已经落盘的安全检查点。

## 9. 交互与线程规范

- 扫描、复制、校验、删除、恢复等耗时操作必须放到 Worker Thread。
- Worker 不直接修改 Tk 控件。
- 统一通过 `queue.Queue` 向 GUI 主线程发送进度、日志和结果。
- GUI 使用 `after()` 周期性消费消息。
- 所有后台任务必须定义：开始、进行中、成功、失败、取消五类 UI 状态。
- 对有持久化副作用的任务，取消必须由核心逻辑提供安全检查点，禁止仅在 UI 层中断线程。

## 10. 兼容性约束

- GUI 技术路线：CustomTkinter。
- 第一阶段依赖锁定在 CustomTkinter 5.2.x，待功能闭环和 Windows 实机回归后再评估 6.x。
- 不使用依赖浏览器内核的 WebView 技术。
- 不依赖系统深色模式。
- 不使用仅 Win10/Win11 可用的视觉 API。

## 11. 页面开发验收清单

每个页面提交前检查：

- [ ] 无页面级硬编码颜色。
- [ ] 无页面级硬编码字体。
- [ ] 间距来自统一 Token。
- [ ] 卡片、按钮优先复用公共组件。
- [ ] 主次按钮层级正确。
- [ ] 危险操作视觉明确并二次确认。
- [ ] 1024×640 最小窗口下不重叠。
- [ ] 长路径和长文件名不会撑破布局。
- [ ] 耗时任务没有放在 GUI 主线程。
- [ ] 破坏性任务取消后，其最新状态已安全落盘。
